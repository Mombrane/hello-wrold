# Java HashMap 哈希碰撞与扰动函数深度解析

> **日期**: 2026-06-02  
> **类别**: Java 核心技术 / 数据结构  
> **摘要**: 深入分析 Java HashMap 中哈希碰撞的数学本质、自然溢出机制、碰撞处理策略，以及扰动函数（disturbance function）的设计原理与性能优化价值。

---

## 1. 引言

在 Java 集合框架中，`HashMap` 是使用频率最高的数据结构之一。其核心性能依赖于哈希函数的分布质量——理想情况下，任意两个键的哈希值应均匀分布在所有桶中。然而，由于哈希值空间（2³²）远小于键的取值空间（无限），哈希碰撞在数学上不可避免。Java 通过一系列精巧的设计——自然溢出、扰动函数、链地址法与红黑树树化——在工程实践中将碰撞的性能代价降至最低。

本文将从数学原理出发，逐层剖析 Java 8 中 `HashMap` 处理哈希碰撞的完整技术链路。

---

## 2. 碰撞的数学本质：鸽巢原理

### 2.1 有限值域与无限输入

Java 中 `hashCode()` 的返回值类型为 `int`，共 2³² 种可能值（约 43 亿）。然而，`String` 的可能组合、`Long` 的取值空间（2⁶⁴）、自定义对象的属性组合均为无限集或远大于 2³² 的集合。根据鸽巢原理（Pigeonhole Principle），将无限集合映射到有限集合，至少存在两个不同元素映射到同一哈希值的必然性。

### 2.2 经典碰撞案例

JDK 中 `String.hashCode()` 的实现公式为：

```
s[0] × 31^(n-1) + s[1] × 31^(n-2) + ... + s[n-1]
```

以下为已知的碰撞对（输出 2112）：

```java
"Aa".hashCode()  → 65×31 + 97  = 2112
"BB".hashCode()  → 66×31 + 66  = 2112
```

通过构造满足线性关系的字符序列，可以生成任意长度的碰撞字符串，例如 `"AaAa"` 与 `"BBBB"`（均为 2031744）。

## 3. 哈希计算中的自然溢出

### 3.1 整数溢出语义

Java 的 `int` 类型使用 32 位补码表示，范围为 [-2³¹, 2³¹-1]。当算术运算的结果超出此范围时，Java 采用**静默回绕（silent wrap-around）**策略——高位比特被直接丢弃，仅保留低 32 位。该行为等价于对 2³² 取模，但由 CPU 在硬件层面完成，无额外指令开销。

### 3.2 溢出作为免费模运算

在 `StringLatin1.hashCode()` 的实现中：

```java
public static int hashCode(byte[] value) {
    int h = 0;
    for (byte v : value) {
        h = 31 * h + (v & 0xff);
    }
    return h;
}
```

每一步 `31 * h + char` 的累加都可能溢出。例如，当 `h` 达到 2 × 10⁹ 时，`31 × h` 约为 6.2 × 10¹⁰，远超 int 上限，溢出后回绕至负半轴。这种设计并非权宜之计——它同时达成两个目标：

1. **零成本取模**：溢出自动完成 mod 2³² 运算；
2. **比特混合增强**：高位信息在溢出过程中向下折叠，增强了低位区域的熵。

溢出回绕的直观类比：如同老式汽车的机械里程表，99999 → 00000，溢出不报错，环上继续滚动。

### 3.3 乘数 31 的选型依据

`String.hashCode()` 选择 31 作为乘数，基于以下考量：

- **奇偶性**：31 为奇数，使得 `31 × h` 的最低位（LSB）不会恒为 0。若使用偶数乘数（如 32），低位将逐步被零填充，碰撞率急剧上升；
- **移位优化**：`31 × h = (h << 5) - h`，JIT 编译器可将其优化为移位与减法指令，性能优于通用乘法；
- **质数性质**：质数乘数在模运算下具有更好的分布特性，减少公因数导致的周期性碰撞。

## 4. HashMap 的碰撞处理：链地址法 + 红黑树

### 4.1 桶索引计算

HashMap 通过 `(n - 1) & hash` 计算桶索引，其中 n 为桶数组长度（始终为 2 的幂）。按位与运算等价于 `hash % n`，但比取模运算快一个数量级。

```java
// 等价替换
int bucket = hash % n;           // 通用取模，含除法
int bucket = hash & (n - 1);     // n 为 2 的幂时的等价优化
```

### 4.2 链地址法

当不同键的哈希值映射到同一桶时，HashMap 使用链地址法（Separate Chaining）处理：

- 同一桶内的多个节点以链表形式串联；
- 查找时先通过 `hashCode()` 定位桶，再遍历链表，通过 `equals()` 逐一比对；
- `equals()` 是最终判等标准，`hashCode()` 仅承担快速定位的职责。

### 4.3 红黑树树化

JDK 8 引入了树化（treeify）策略，当链表长度 ≥ `TREEIFY_THRESHOLD`（8）且桶数组容量 ≥ `MIN_TREEIFY_CAPACITY`（64）时，将链表转换为红黑树：

```
查找复杂度：
  链表: O(n)  →  红黑树: O(log n)
```

这一设计消除了退化攻击（构造大量碰撞键使链表退化为 O(n) 查找）的安全隐患。当节点数减少至 ≤ 6 时，红黑树退化为链表（untreeify），避免不必要的内存开销。

### 4.4 扩容与重哈希

当 `size > capacity × loadFactor`（默认 0.75）时触发扩容：

- 容量翻倍（16 → 32 → 64 → …）；
- 所有节点重新计算桶索引并迁移；
- JDK 8 优化：利用容量为 2 的幂的特性，每个节点最多迁移到两个目标桶之一（原索引 或 原索引 + 旧容量），无需重新计算哈希值。

## 5. 扰动函数：一行代码的工程智慧

### 5.1 动机分析

桶索引计算 `(n - 1) & hash` 的固有缺陷在于：当 n 较小时（如默认容量 16），n-1 的低位掩码仅覆盖少量比特：

```
n = 16 → n-1 = 15 → 二进制约：0000 0000 0000 1111（仅低 4 位参与）
n = 32 → n-1 = 31 → 二进制约：0000 0000 0001 1111（仅低 5 位参与）
```

高 28 位（或高 27 位）的信息被**完全丢弃**。若两个键的 hashCode 仅在高位不同而低位相同，它们将必然映射到同一桶——无论高位差异多大。

典型案例：

- `Float` 键：`Float.hashCode()` 即 `floatToRawIntBits()`，小数部分的低位模式高度重复；
- 时间戳键：高位字节随时间变化，低位字节因对齐规律高度相似；
- 自定义对象：若 `hashCode()` 实现不够均匀，低位差异可能极小。

### 5.2 扰动函数实现

JDK 8 中 `HashMap.hash()` 的实现：

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

运算过程：

```
原始 hashCode:  高16位                           低16位
               ┌─────────────────────┬─────────────────────┐
               │ 0001 1010 1100 0011 │ 0000 0000 0000 0101 │
               └─────────────────────┴─────────────────────┘
                                         ↘
h >>> 16:      ┌─────────────────────┬─────────────────────┐
               │ 0000 0000 0000 0000 │ 0001 1010 1100 0011 │
               └─────────────────────┴─────────────────────┘
                                         ↓  XOR
混合后:        ┌─────────────────────┬─────────────────────┐
               │ 0001 1010 1100 0011 │ 0001 1010 1100 0110 │
               └─────────────────────┴─────────────────────┘
                高16位保持不变          低16位携带了高区特征 ↑
```

通过将高 16 位的信息"折叠"进低 16 位，桶索引计算使用的低位不再丢失高位信息。一次运算，将 32 位完整熵传递至索引层。

### 5.3 设计选择分析

#### 5.3.1 为什么使用 XOR？

| 运算 | 偏向 | 问题 |
|------|------|------|
| AND (`&`) | 偏向 0（任何位与 0 = 0） | 丢失信息，输出熵降低 |
| OR (`\|`) | 偏向 1（任何位与 1 = 1） | 丢失信息，输出熵降低 |
| XOR (`^`) | 无偏向（0 和 1 各 50%） | 信息完整，均匀混合 ✅ |

XOR 保持了每一位的均衡分布概率，确保高低位信息无损融合。

#### 5.3.2 为什么移 16 位？

int 为 32 位，右移 16 位恰好将高低半区对齐：

- 移位过少（如 8 位）：高 24 位信息未充分混合到低 8 位；
- 移位过多（如 24 位）：参与混合的高区信息过少；
- 16 位是对半切的最优解，最大化了参与混合的信息量。

#### 5.3.3 JDK 7 → JDK 8 的扰动简化

JDK 7 实现了 4 轮扰动（5 次异或 + 4 次位移）：

```java
// JDK 7: 多轮扰动
h ^= (h >>> 20) ^ (h >>> 12);
h ^= (h >>> 7) ^ (h >>> 4);
```

JDK 8 将扰动简化为单次 `h ^ (h >>> 16)`，背后逻辑是：

1. **红黑树兜底**：即使扰动不完美导致碰撞，树化将退化代价从 O(n) 降至 O(log n)；
2. **性能预算重分配**：节省的扰动计算开销远大于轻微碰撞增加的开销；
3. **实测验证**：单次扰动在绝大多数场景下已实现足够的分布均匀性。

这是 JDK 8 架构设计中最具代表性的"以结构换算法"策略——用更复杂的数据结构（红黑树）换取更简洁的哈希算法。

## 6. 完整技术链路

```
                 key.hashCode()
                      ↓
              h ^ (h >>> 16)          ← 扰动函数：折叠高位信息
                      ↓
           [n-1] & hash               ← 桶索引计算：取低位（已含高位特征）
                      ↓
               ┌──────┴──────┐
               ↓              ↓
        桶中查找         桶为空则新建
               ↓
        ┌──────┴──────┐
        ↓              ↓
    链表遍历      红黑树查找（≥8 节点）
        ↓              ↓
    equals() 判等  compare/equals 判等
```

## 7. 与其他哈希实现的对比

### 7.1 ConcurrentHashMap 的 spread()

`ConcurrentHashMap` 使用 `HASH_BITS` 掩码后的 `(h ^ (h >>> 16)) & 0x7fffffff` 确保哈希值为非负，配合其分段锁机制中的特殊哨兵节点（负数表示 MOVED/TREEBIN/RESERVED 状态）。

### 7.2 Redis 哈希槽的 CRC16

Redis Cluster 使用 CRC16 对 key 计算哈希后取模 16384 分配槽位。与 HashMap 的差异在于：

- CRC16 是完整性校验算法，分布特性优于简单乘法哈希；
- Redis 的槽位切换涉及跨节点数据迁移，对碰撞的容忍度远低于单机 JVM；
- HashMap 可接受少量碰撞（红黑树兜底），Redis 的碰撞意味着节点间负载不均。

### 7.3 Golang map 的哈希机制

Go 的 map 使用 AES-based hash 函数（`runtime.memhash`），在编译期根据 CPU 架构选择最优实现。与 Java 相比，Go 的哈希种子在进程启动时随机生成，且每个 map 实例独立使用随机种子，天然抵御哈希碰撞攻击（HashDoS）。

---

## 8. 总结

Java HashMap 的哈希碰撞处理体现了以下工程原则：

1. **数学不可违抗**：碰撞是鸽巢原理的必然结论，工程师的职责是管理而非消除它；
2. **溢出即特性**：Java int 的自然溢出不是 bug，而是零成本的 mod 2³² 运算与免费的比特混合器；
3. **扰动即补偿**：一行 `h ^ (h >>> 16)` 将 HashMap 在高位变化型键上的退化风险消解于无形；
4. **结构换算法**：JDK 8 用红黑树替换多轮扰动，是以空间换时间、以结构复杂换算法简洁的教科书案例。
